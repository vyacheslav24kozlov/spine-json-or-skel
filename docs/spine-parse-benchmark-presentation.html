Замер парсинга Spine

Как runParseBenchmark измеряет скорость readSkeletonData() и почему JSON и SKEL парсятся с разной скоростью

src/shared/parseBenchmark.ts src/shared/utils.ts src/shared/metrics.ts

Бенчмарк многократно парсит один и тот же skeleton и собирает статистику: среднее/мин/макс время, «пропущенные кадры» и самую долгую блокировку. Сравниваются два формата — JSON (текст) и SKEL (бинарь).

loadSpineAssets fetch atlas + skeleton
→
warmup ×3 прогрев JIT
→
recordParseSample ×N замер каждой итерации
→
ParseBenchmarkResult агрегированные метрики

runParseBenchmark: общая структура

const { format, instanceCount, warmupCount = 3 } = options;
const assets = await loadSpineAssets(format);

// 1. Прогрев — без измерений
for (let i = 0; i < warmupCount; i += 1) {
  parseSkeletonData(assets, format);
}

// 2. Синхронизация с кадром браузера
await waitForNextFrame();

// 3. Аккумулятор статистики
const acc = { durations: [], droppedFrames: 0, longestFrameGapMs: 0 };

// 4. Замеряем instanceCount итераций
for (let i = 0; i < instanceCount; i += 1) {
  recordParseSample(assets, format, acc);
  await waitForNextFrame(); // пауза между итерациями
}

// 5. Агрегация
const totalParseMs = acc.durations.reduce((s, v) => s + v, 0);
Ключевой принцип: ассеты загружаются один раз, а измеряется только повторяемая часть — сам парсинг readSkeletonData(). Сеть и atlas в замер не попадают.

Перед замером: loadSpineAssets

Самый первый шаг runParseBenchmark — await loadSpineAssets(format). Он выполняется один раз, до прогрева, поэтому сеть и подготовка данных в тайминг парсинга не попадают. 

const [atlasResponse, skeletonResponse] = await Promise.all([
  fetch("/assets/symbols.atlas"),
  fetch(format === "json"
    ? "/assets/animation.json"
    : "/assets/animation.skel"),
]);

const atlas = new TextureAtlas(await atlasResponse.text());

if (format === "json") {
  const skeletonText = await skeletonResponse.text();          // строка
  return { atlas, skeletonBytes: new Uint8Array(), skeletonText,
           fileSizeBytes: new TextEncoder().encode(skeletonText).length };
}

const skeletonBytes = new Uint8Array(await skeletonResponse.arrayBuffer());
return { atlas, skeletonBytes, skeletonText: "",
         fileSizeBytes: skeletonBytes.byteLength };            // байты

Что делает

  • Параллельно (Promise.all) грузит atlas и skeleton через fetch.
  • Atlas сразу парсится в TextureAtlas — он одинаков для обоих форматов.
  • Skeleton читается по-разному: JSON — как text() в skeletonText; SKEL — как arrayBuffer() → Uint8Array в skeletonBytes.
  • Считает fileSizeBytes для отчёта (через TextEncoder для JSON, byteLength для SKEL).

Почему до warmup

  • Замеряем только парсинг, а не загрузку — ассеты уже в памяти к моменту измерений.
  • Один и тот же LoadedSpineAssets переиспользуется во всех итерациях: warmup и все recordParseSample парсят из готовых skeletonText / skeletonBytes.

На выходе — LoadedSpineAssets { atlas, skeletonBytes, skeletonText, fileSizeBytes }. Дальше с ним работают warmup и цикл замеров.

Шаг 1: warmup (прогрев)

Перед измерениями skeleton парсится warmupCount раз (по умолчанию 3) без записи результата. 

for (let index = 0; index < warmupCount; index += 1) {
  parseSkeletonData(assets, format);
}

Зачем это нужно

  • JIT-компиляция: V8 сначала исполняет код интерпретатором, и только после нескольких прогонов оптимизирует «горячие» функции. Первый парс всегда медленнее.
  • Прогрев кэшей и аллокатора: подгружаются inline caches, формы объектов (hidden classes) стабилизируются.
  • Честное сравнение: и JSON, и SKEL получают одинаковый прогрев — измеряем стабильное состояние, а не cold-start.

Без прогрева первые замеры были бы аномально большими и исказили бы avg и max.

Шаг 2: синхронизация с кадром

Перед циклом и между итерациями вызывается waitForNextFrame() — обёртка над requestAnimationFrame. 

async function waitForNextFrame(): Promise<number> {
  return new Promise((resolve) => {
    requestAnimationFrame((timestamp) => resolve(timestamp));
  });
}

Зачем перед циклом

Начинаем замер «с чистого кадра» — не в середине занятого фрейма, где браузер уже что-то делает. Это снижает шум первого замера.

Зачем между итерациями

Даём браузеру отрисовать кадр, выполнить GC и обработать события. Каждая итерация стартует в сопоставимых условиях, а не упирается в забитую очередь микротасков.

Важно: await waitForNextFrame() стоит вне замеряемого интервала. В тайминг попадает только синхронный parseSkeletonData.

Шаг 3: recordParseSample — сам замер

Одна итерация: парсим один раз, считаем длительность и обновляем аккумулятор. 

export function recordParseSample(assets, format, acc) {
  const startedAt = performance.now();   // высокоточный таймер
  parseSkeletonData(assets, format);     // ← измеряемая работа
  const endedAt = performance.now();

  const duration = endedAt - startedAt;  // мс на один парс
  acc.durations.push(duration);

  acc.droppedFrames += estimateDroppedFrames(duration);
  acc.longestFrameGapMs = Math.max(acc.longestFrameGapMs, duration);
}

Что именно меряется

  • performance.now() — монотонный таймер с суб-миллисекундной точностью (не зависит от системных часов).
  • Между двумя замерами — только parseSkeletonData: создание AtlasAttachmentLoader + readSkeletonData().
  • Результат каждой итерации складывается в массив durations для последующей агрегации.

Метрики из metrics.ts

Производные показатели считаются из «бюджета кадра» 60 FPS:

const TARGET_FPS = 60;
export const FRAME_BUDGET_MS = 1000 / TARGET_FPS; // ≈ 16.67 мс

export function estimateDroppedFrames(blockingMs: number): number {
  if (blockingMs <= FRAME_BUDGET_MS) {
    return 0;
  }
  return Math.floor(blockingMs / FRAME_BUDGET_MS);
}

droppedFrames

Парсинг синхронный и блокирует главный поток. Если он длится дольше одного кадра (~16.67 мс), браузер не успевает отрисоваться — кадры «выпадают».

Пример: парс на 40 мс → floor(40 / 16.67) = 2 пропущенных кадра.

longestFrameGapMs

Math.max по всем итерациям — самая долгая разовая блокировка. Показывает worst-case «фриз» интерфейса от одного парса.

Это перевод «миллисекунд парсинга» в понятный для UI язык: сколько кадров пользователь реально потеряет.

Шаг 5: агрегация результата

После цикла из массива durations собирается ParseBenchmarkResult: 

const totalParseMs = acc.durations.reduce((sum, v) => sum + v, 0);

return {
  format,
  instanceCount,
  fileSizeBytes: assets.fileSizeBytes,
  totalParseMs,
  avgParseMs: totalParseMs / instanceCount,
  minParseMs: Math.min(...acc.durations),
  maxParseMs: Math.max(...acc.durations),
  droppedFramesDuringParse: acc.droppedFrames,
  longestFrameGapMs: acc.longestFrameGapMs,
};
Поле Как считается О чём говорит
avgParseMs total / instanceCount типичная стоимость одного парса
minParseMs Math.min(durations) лучший случай (прогретый путь)
maxParseMs Math.max(durations) худший случай (GC, шум)
fileSizeBytes из loadSpineAssets размер исходных данных

Почему JSON и SKEL парсятся по-разному

Разница не в результате — обе ветки строят одинаковый SkeletonData. Разница в стоимости чтения:

JSON → SkeletonJson

const json = new SkeletonJson(loader);
return json.readSkeletonData(
  assets.skeletonText // строка
);
  • Сначала JSON.parse токенизирует текст и строит большое промежуточное дерево JS-объектов.
  • Числа хранятся как текст → нужна конвертация "171.5" → number.
  • Ключи-строки, кавычки, пробелы — лишние байты и аллокации.
  • Больше работы для GC из-за временных объектов.

SKEL → SkeletonBinary

const bin = new SkeletonBinary(loader);
return bin.readSkeletonData(
  assets.skeletonBytes // Uint8Array
);
  • Последовательное чтение байт из Uint8Array — без промежуточного дерева.
  • Числа уже в бинарном виде (float/varint) → читаются напрямую, почти без конвертаций.
  • Нет парсинга строк-разделителей и структуры.
  • Меньше аллокаций → меньше нагрузка на GC.

Итог

  1. Нет JSON.parse()

    JSON.parse — очень быстрый, но не бесплатный. Для большого файла: 2–10 ms иногда больше. SKEL этого этапа вообще не имеет.

  2. Меньше аллокаций памяти

    JSON создаёт огромное дерево временных объектов: 
    {
  bones: [...],
  slots: [...],
  animations: {...}
}
    которое затем Spine снова преобразует в свои структуры. Получается двойная работа: 
    JSON text
    ↓
JS Object
    ↓
Spine Object
    Для SKEL: 
    Binary
    ↓
Spine Object
    Промежуточного слоя нет.

  3. Меньше нагрузка на GC

    JSON создаёт:
    • строки
    • массивы
    • объекты
    которые после парсинга становятся мусором. Потом срабатывает GC. SKEL создаёт значительно меньше временных объектов.

JSON vs SKEL: сводка по замеру

JSON SKEL
Вход в парсер string (skeletonText) Uint8Array (skeletonBytes)
Парсер SkeletonJson SkeletonBinary
Размер файла больше (~21 KB) меньше (~9.5 KB)
Промежуточное дерево да (JSON.parse) нет (поток байт)
Конвертация чисел строка → число читается напрямую
Типичный avgParseMs выше ниже
Результат идентичный SkeletonData

Меньше байт + меньше работы на байт → у SKEL обычно ниже avgParseMs, maxParseMs и droppedFrames. На очень маленьких скелетах разница может быть в пределах погрешности — поэтому и нужен прогон по instanceCount итераций.

Краткое резюме

  1. loadSpineAssets один раз грузит ассеты — сеть в замер не входит.
  2. warmup ×3 убирает эффект cold-start / JIT перед измерениями.
  3. waitForNextFrame синхронизирует итерации с кадром браузера и стоит вне таймера.
  4. recordParseSample меряет один синхронный парс через performance.now() и копит durations.
  5. metrics переводят мс в «пропущенные кадры» и worst-case блокировку относительно бюджета 60 FPS.
  6. SKEL быстрее JSON: бинарь меньше, читается потоком байт без промежуточного дерева и без конвертации строк в числа.
