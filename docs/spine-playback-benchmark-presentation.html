Playback benchmark Spine

Как runPlaybackBenchmark измеряет создание runtime-инстансов и отыгрывание анимаций — и почему SKEL быстрее на этапе создания

src/shared/playbackBenchmark.ts src/shared/utils.ts src/shared/metrics.ts

Playback benchmark — это полный сценарий «как в игре»: загрузка через AssetManager, парсинг в SkeletonData, массовое создание Skeleton + AnimationState, раскладка на canvas и цикл update → render в WebGL.

loadAssetsForPlayback atlas + json/skel + текстуры
→
parseSkeletonData один раз → SkeletonData
→
benchmarkCreateRuntimeInstances замер создания N инстансов
→
runPlaybackBenchmark loop замер FPS / frame time

runPlaybackBenchmark: общая структура

export async function runPlaybackBenchmark(options) {
  const assets = await loadAssetsForPlayback(canvas, format);  // сеть, не в метриках
  const skeletonData = parseSkeletonData(assets, format);      // парс 1×, не в create-метриках

  const instanceCreateBenchmark = benchmarkCreateRuntimeInstances(
    skeletonData, animationName, instanceCount,
  );
  const instances = instanceCreateBenchmark.instances;

  // WebGL + раскладка — вне замера playback-метрик
  const renderer = new SceneRenderer(canvas, context);
  layoutInstances(instances, viewportWidth, viewportHeight);

  // Цикл отыгрывания — замер frame time
  while (performance.now() < endAt) {
    await requestAnimationFrame((timestamp) => {
      frameTimesMs.push(deltaMs);
      instances.forEach((i) => updateRuntimeInstance(i, deltaSec));
      // clear + drawSkeleton × N
    });
  }

  const stats = summarizeFrameTimes(frameTimesMs);
  return { ...stats, instanceCreate: instanceCreateBenchmark };
}
Два независимых блока метрик: создание инстансов (benchmarkCreateRuntimeInstances) и playback (цикл rAF + summarizeFrameTimes). Загрузка ассетов и layoutInstances в отчёт не попадают.

Подготовка: loadAssetsForPlayback

В отличие от parse-benchmark (чистый fetch), playback грузит всё через AssetManager из @esotericsoftware/spine-webgl — включая текстуры для GPU. 

const assetManager = new AssetManager(context, "/assets/");
assetManager.loadTextureAtlas("symbols.atlas");

if (format === "json") {
  assetManager.loadText("animation.json");
} else {
  assetManager.loadBinary("animation.skel");
}

while (!assetManager.isLoadingComplete()) {
  await assetManager.loadAll();
  await requestAnimationFrame(resolve);  // не блокируем UI
}

Что возвращается

Тот же LoadedSpineAssets, что и в parse-benchmark:

  • atlas — готовый TextureAtlas
  • skeletonText или skeletonBytes
  • fileSizeBytes

Не входит в метрики

Сеть, декодирование WebP, инициализация WebGL-контекста — всё это происходит до замеров создания и playback.

benchmarkCreateRuntimeInstances: что создаётся

Одна итерация — вызов createRuntimeInstance: из шаблона SkeletonData строится пара «скелет + машина анимаций». 

export function createRuntimeInstance(skeletonData, animationName) {
  const skeleton = new Skeleton(skeletonData);
  const animationStateData = new AnimationStateData(skeletonData);
  const animationState = new AnimationState(animationStateData);
  animationState.setAnimation(0, animationName, true);  // loop
  return { skeleton, animationState };
}

Что происходит внутри

  • Skeleton — копирует кости, слоты, draw order из SkeletonData; готов к pose/transform.
  • AnimationStateData — строит таблицы микширования анимаций из данных skeleton.
  • AnimationState + setAnimation — ставит трек 0 на анимацию (например, idle) в loop.

Файл JSON/SKEL не читается при создании инстанса — работа идёт только с уже распарсенным SkeletonData.

benchmarkCreateRuntimeInstances: как меряется

export function benchmarkCreateRuntimeInstances(
  skeletonData, animationName, instanceCount, warmupCount = 3,
) {
  // 1. Прогрев — без записи
  for (let i = 0; i < warmupCount; i += 1) {
    createRuntimeInstance(skeletonData, animationName);
  }

  // 2. Замер каждого инстанса
  for (let i = 0; i < instanceCount; i += 1) {
    const startedAt = performance.now();
    instances.push(createRuntimeInstance(skeletonData, animationName));
    const duration = performance.now() - startedAt;
    createDurations.push(duration);

    droppedFramesDuringCreate += estimateDroppedFrames(duration);
    longestFrameGapMs = Math.max(longestFrameGapMs, duration);
  }

  return { instances, totalCreateMs, avgCreateMs, minCreateMs, maxCreateMs, ... };
}

Warmup ×3

Как в parse-benchmark: прогреваем JIT и аллокатор до измерений. Прогретые инстансы выбрасываются — в массив попадают только замеренные.

Один таймер на инстанс

performance.now() оборачивает ровно один вызов createRuntimeInstance. Между итерациями нет waitForNextFrame — все 100 создаются подряд синхронно.

Цикл playback: что происходит каждый кадр

После создания инстансов запускается цикл на durationSec секунд. Каждый кадр — полный update + render всех N скелетов. 

requestAnimationFrame((timestamp) => {
  const deltaSec = (timestamp - previousTimestamp) / 1000;
  frameTimesMs.push(deltaSec * 1000);           // ← метрика playback

  instances.forEach((instance) => {
    updateRuntimeInstance(instance, deltaSec);
  });

  gl.clear(COLOR_BUFFER_BIT);
  renderer.begin();
  instances.forEach((instance) => {
    renderer.drawSkeleton(instance.skeleton, true);
  });
  renderer.end();
});
export function updateRuntimeInstance(instance, deltaSec) {
  instance.animationState.update(deltaSec);       // продвижение таймлайна
  instance.animationState.apply(instance.skeleton); // ключи → pose
  instance.skeleton.updateWorldTransform(Physics.update);
}

Что входит в frame time

  • Update всех AnimationState и world transform
  • WebGL clear + drawSkeleton × instanceCount
  • Накладные расходы rAF и renderer.resize

Формат JSON/SKEL в этом цикле не участвует — инстансы уже созданы, отличается только то, каким парсером был построен исходный SkeletonData.

Метрики playback (summarizeFrameTimes)

const TARGET_FPS = 60;
const FRAME_BUDGET_MS = 1000 / 60;  // ≈ 16.67 ms

export function summarizeFrameTimes(frameTimesMs) {
  const avgFrameMs = sum(frameTimesMs) / length;
  const sorted = [...frameTimesMs].sort();
  const p95Index = floor(length * 0.95);

  return {
    avgFps: 1000 / avgFrameMs,
    minFps: 1000 / max(frameTimesMs),   // худший кадр → минимальный FPS
    droppedFrames: count(frameMs > FRAME_BUDGET_MS * 1.5),
    frameTimeP95Ms: sorted[p95Index],
  };
}
Поле в UI Поле в коде Смысл
Средний FPS avgFps 1000 / среднее время кадра за весь прогон
Минимальный FPS minFps Обратное от самого долгого кадра (worst spike)
Кадров totalFrames Сколько rAF-итераций уложилось в durationSec
Просадки (>150% budget) droppedFrames Кадры длиннее 25 ms (1.5 × 16.67) — заметные лаги
P95 frame time frameTimeP95Ms 95% кадров быстрее этого значения — устойчивость, не только avg

Playback-метрики отвечают на вопрос: «выдержит ли сцена N одновременных анимаций при 60 FPS?» Создание инстансов — отдельный одноразовый cost при спавне.

Почему SKEL быстрее создаёт 100 инстансов?

Ваши результаты: JSON 4.00 ms vs SKEL 2.80 ms (~1.43×, экономия 1.2 ms на 100 инстансов). Главный ответ:

При создании инстанса файл не парсится повторно

Разница идёт не от «SKEL быстрее читает .skel в цикле», а от того, какой SkeletonData уже лежит в памяти после parseSkeletonData — а он построен разными парсерами.

Цепочка для JSON

animation.json (текст)
  → SkeletonJson.readSkeletonData()
  → SkeletonData (из JS-дерева)
  → new Skeleton(skeletonData) × 100
  → new AnimationStateData(skeletonData) × 100
  • Парсер прошёл через JSON.parse и обход объектов
  • Больше промежуточных строк и объектов при построении данных
  • SkeletonData может быть «тяжелее» для клонирования

Цепочка для SKEL

animation.skel (байты)
  → SkeletonBinary.readSkeletonData()
  → SkeletonData (прямое чтение)
  → new Skeleton(skeletonData) × 100
  → new AnimationStateData(skeletonData) × 100
  • Бинарь меньше (~9.5 KB vs ~21 KB)
  • Меньше аллокаций при первичном парсинге
  • Компактнее граф данных → быстрее обход при new Skeleton

Детали: почему разница небольшая, но заметная

1. Наследие от парсинга

createRuntimeInstance копирует кости, слоты, ссылки на анимации из SkeletonData. Если JSON-парсер оставил более фрагментированный граф (строки имён, больше мелких объектов), каждое клонирование чуть дороже.

2. Масштаб эффекта

Разница ~0.01 ms на инстанс — это доли процента от бюджета кадра. На 100 инстансах накапливается в ~1.2 ms. На 10 000 спавнов в одном кадре уже ~1 с — формат начинает иметь значение.

3. Шум измерений

При субмиллисекундных таймингах важен разброс: у SKEL max = 0.50 ms, у JSON max = 0.20 ms — SKEL быстрее в среднем, но с большим spike. Это GC или квантование performance.now(), а не «SKEL всегда стабильнее».

4. Playback — паритет

После создания инстансы идентичны по логике. FPS и P95 frame time должны совпадать при одном instanceCount: в цикле нет ветвления JSON/SKEL, только update + WebGL draw.

Итог: SKEL выигрывает на создании потому, что до замера skeleton уже распарсен в более «лёгкий» SkeletonData, и клонирование Skeleton + AnimationState обходится дешевле. Это следствие преимущества бинарного формата на этапе readSkeletonData, а не отдельной магии SKEL при new Skeleton().

Краткое резюме

  1. runPlaybackBenchmark — загрузка (AssetManager) → парс → замер создания N инстансов → WebGL playback loop.
  2. benchmarkCreateRuntimeInstances — warmup ×3, затем performance.now() на каждый createRuntimeInstance; метрики: total/avg/min/max, droppedFramesDuringCreate, longestFrameGapMs.
  3. Playback-метрики — delta rAF → avgFps, minFps (от max frame), droppedFrames (>25 ms), frameTimeP95Ms.
  4. JSON 4.00 ms vs SKEL 2.80 ms — файлы в цикле не читаются; SKEL быстрее, потому что его SkeletonData построен компактнее после бинарного парсинга, и клонирование инстансов дешевле.
  5. Разница мала на одном инстансе (~0.01 ms), но масштабируется с количеством спавнов; при playback формат почти не влияет.
